# 日文卡片的 furigana（ruby）顯示

詞彙沿用 [`/CONTEXT.md`](../../../CONTEXT.md)。決策以 ADR-NNNN 引用自 [`docs/adr/`](../../adr/)。本規格屬 v1 之後，且是加法式的：它只改變卡片*如何被繪製*，絕不改變卡片如何被儲存、排程或選取。

## 問題陳述

日文卡片的正面常常是一串學習者正在習得讀音的漢字。在紙上與 Anki 裡，那個讀音以 *furigana* 呈現：印在漢字上方的小假名（ruby text）。LearnWhile 沒有任何辦法顯示讀音，所以日文 deck 作者只有兩個都不好的選擇：把讀音行內塞進同一個欄位（這會弄亂提示，而且在問題面等於把答案洩出去），或者乾脆不放，於是失去卡片上最有用的那一項資訊。

有兩個限制讓這件事在我們的表面上並不簡單：

1. 終端機是一個由全尺寸儲存格構成、只有單一字體大小的固定格點。真正的排版式 ruby（在 base 字符上方的半高假名）在物理上不可能。唯一忠實的呈現是*堆疊式*的：讀音自成一整行、就在 base 行的正上方，並逐欄對齊。
2. 漢字與假名佔兩個顯示欄寬，而讀音通常比它蓋住的漢字更寬。對齊必須以顯示欄寬計算，而不是以字元或位元組計算，否則讀音會從它的漢字上偏移。這正是測試 harness 的 `buffer_text` 被修正去尊重的那套寬字元計算（commit `7b19b57`）。

## 解法

讓卡片作者以 **Anki 相容的 furigana 標記**行內標注讀音，並把這些標記渲染成讀音疊在 base 上方的版面。讀音**只在答案面**顯示。在問題面，帶標記的文字渲染成純漢字，所以一張「讀出這個漢字」的卡片仍是誠實的回想測驗（這呼應 ADR-0002 拒絕洩漏複習所要測驗之物的原則，只是套用在揭示邊界而非排程器）。

儲存、seeding、hashing、選卡或 FSRS 都不改。卡片模型本來就在 `front`/`back` 裡存任意 UTF-8；標記以普通文字住在那裡，而每個既有子系統都把它當成不透明的。Furigana 純粹是 Renderer 加上一個新的純粹 module（負責解析與排版該標記）的事。

## 使用者故事

1. 身為日文 deck 作者，我想在卡片正面寫 `勉強[べんきょう]`，讓讀音附在漢字上，而不需要另設欄位或改 schema。
2. 身為學習者，我想在回想時正面只顯示漢字，這樣一張測驗讀音的卡片不會直接把答案交給我。
3. 身為學習者，我想在揭示時讀音出現在它的漢字正上方，讓我能像 ruby text 本該被讀的方式，一眼核對我的回想。
4. 身為帶著一個長標注句的學習者，我想讀音與它的漢字作為一個單元一起折行，這樣讀音永遠不會落到與它所屬漢字不同的行上。
5. 身為一張全英文（或已是純日文）卡片的作者，我想它渲染得跟今天一模一樣，這樣對不使用讀音的卡片來說，加這個功能沒有任何代價。

## 標記

我們原封不動採用 Anki 的 furigana 格式，這樣 deck 可雙向互通，而且規則是作者可能已經知道的那一套。

- **形式。** `base[reading]`。方括號內的文字是緊接 `[` 之前那串非空白字元的讀音。
- **分隔空白。** 一個單一空白把一個 furigana 單元與它前面的文字分開，並在 render 時被消耗（不顯示）。它唯一的工作是界定 base 的範圍。例：在 `この 間[あいだ]` 裡，這個空白讓 `この` 不會被拉進 base，所以只有 `間` 拿到讀音 `あいだ`。不是緊接在 `[…]` 群組之前的空白是字面的。
- **送假名與相鄰詞自然成立。** `食[た]べる` 讓 た 疊在 食 上、べる 為純文字。`日本[にほん]語[ご]` 把 にほん 放在 日本 上、ご 放在 語 上，因為每個 `]` 都界定了下一段 base 的範圍。
- **跳脫。** 沒有跳脫字元，與 Anki 一致。需要在顯示文字中放字面方括號的作者，改用全形 `［ ］`（`U+FF3B`／`U+FF3D`），它們是不同的碼位，永遠不會被當成標記。

**參考 parser（Anki）：** reader 以 ` ?([^ >]+?)\[(.+?)\]` 掃描，並提供三種呈現：`furigana:`（ruby）、`kanji:`（只有 base，去掉讀音與分隔空白）、`kana:`（只有讀音）。我們的兩種 render 模式正好是 Anki 的 `kanji:`（問題面）與 `furigana:`（答案面）。我們把字元類別裡的 `>` 拿掉，因為我們沒有要防的 HTML，於是 base = 一串在 `[` 處結束的、最大長度的非空白字元。

來源：
[Anki manual: field replacements](https://docs.ankiweb.net/templates/fields.html)、
[obynio/anki-japanese-furigana `reading.py`](https://github.com/obynio/anki-japanese-furigana/blob/master/reading.py)。

## 渲染

### 兩種 render 模式

對一段給定的欄位字串，furigana module 產生下列其中之一：

- **Base-only（問題面）。** 依序串接每一段 base 與每一段字面（非標記）片段，去掉每個單元的分隔空白與每個 `[reading]`。`勉強[べんきょう]` 變成 `勉強`。沒有 `[…]` 的欄位原樣返回。
- **Stacked（答案面）。** 產生一條**讀音行**與一條**base 行**，兩者顯示寬度相等，並對齊到每個讀音置中在它的 base 上方。

### 向後相容

如果一個欄位不含 `[…]` 標記，兩種模式都返回原字串，Renderer 就跟今天完全一樣地繪製它（單一 `Line`，由 ratatui 折行）。只有在至少存在一個標記時才會走進 stacked 路徑。這讓每個既有測試與每張英文／純文字卡片維持逐位元組不變。

### 各模式用在哪裡

| Pane state | `front` | `back` |
|---|---|---|
| `Question` | base-only | （不顯示） |
| `Answer`   | stacked   | stacked |

於是正面的讀音在回想時被藏起、在揭示時出現在漢字上方，而一個本身含漢字的 back 也得到同樣處理。這實現了「只在答案面」的決策。

### 堆疊版面演算法

全程以**顯示欄寬**運算，使用 ratatui 對 `str` 的 `CellWidth`（已是相依套件，且是 renderer 與測試 harness 用的同一個寬度來源，包含它對半形片假名濁點的調整）。不加新 crate。

1. **Tokenize** 欄位：掃描參考 regex，得到一串有序的單元。match 之間／周圍的文字成為純文字單元（`reading = None`）；每個 match 成為一個 ruby 單元 `{ base, reading }`。丟掉 match 前的分隔空白。
2. **量每個單元的寬。** `unit_cols = max(width(base), width(reading))`（純文字單元的 `width(reading)` 是 0）。
3. **把每個單元 render 成兩段等寬片段**，把較窄的置中在較寬的之上：`base_piece = center(base, unit_cols)`、`read_piece = center(reading_or_blank, unit_cols)`，其中 `center` 以空白補齊，左側補 `(unit_cols - width)/2`。
4. **以單元為單位折行。** 貪婪地把單元累積成一個行群組，直到下一個單元會超過 pane 的內寬為止；絕不把一個單元拆到不同行。把每個群組輸出成一對 `(reading_line, base_line)`。
5. Renderer 對每個群組先送讀音 `Line` 再送 base `Line`，對這些預先排好的行停用 `Wrap`（我們已經折過行了）。群組之間以一條空白行分隔以利閱讀。

範例（`front = "「 勉強[べんきょう]」は 英語[えいご]で 何[なん]と 言[い]いますか？"`，答案面）：

```
    べんきょう      えいご    なん  い
「  勉強  」は    英語  で  何  と  言いますか？
```

讀音 `べんきょう`（5 個假名、10 欄）比 `勉強`（4 欄）寬，所以該單元寬 10 欄，漢字置中在讀音下方。純文字段（`「`、`」は`、`で`、`と`、`いますか？`）佔自己的寬度，上方留白。

### Renderer 整合

`PaneState` 仍舊攜帶 `front`/`back` 的原始 `&str`（標記是渲染的事，所以 host 與 learning engine 從不看到解析後的形式）。`renderer::draw` 新增：從 `areas[0]` 減去邊框得到的內寬、對每個可見欄位呼叫一次 furigana module，以及一個分支：渲染今天那條單一折行 `Line`（無標記），或渲染堆疊、預先折行的 `Line` 序列（有標記）。所有新邏輯都在 `renderer.rs` 與一個新的 `src/furigana.rs` 裡。

## 什麼不變

- **Schema 與 storage。** `front`/`back` 仍存作者輸入的原始文字，含標記在內。沒有新欄位、沒有 migration。
- **`seed` / `parse_tsv`。** TSV 解析在第一個 tab 切分並修剪兩端。標記文字不含 tab，其內部空白都在同一行內，所以毫髮無傷地存活。
- **`content_hash` / 去重。** hash 是對原始 `front`+`back` 計算的。因此 `勉強` 與 ` 勉強[べんきょう]` 是不同的卡片，這是對的：它們是不同的提示。
- **選卡、FSRS、Review flow、Trigger、IPC。** 完全不受影響。

## 管理面

`learnwhile cards` 原樣印出 `card.front`，所以一張帶標記的卡片會列成 ` 勉強[べんきょう]`。這是刻意的：管理／除錯用的列表應該顯示作者到底輸入了什麼，而那正是讀音渲染錯誤時作者需要的。（若之後覺得這很吵，在那裡改成 base-only 呈現是一行的後續工作，不屬於本規格。）

## 邊界情況

- **讀音比 base 寬**是常態，由 `unit_cols = max(...)` 處理。
- **一個 `[` 沒有對應的 `]`，或空的 `[]`**，不會 match regex，在兩面都留作字面文字。畸形的標記退化為可見的原始碼，絕不 panic。
- **同一段 base 混用多種文字**（`お茶[ちゃ]` 把 ちゃ 放在 お茶 上）：與 Anki 一致。作者插入一個分隔空白（`お 茶[ちゃ]`）把讀音的範圍收到只有 茶。
- **零高度 pane／非常窄的寬度**已由 `Constraint::Min(3)` 夾住；一個比內寬還寬的單元被單獨放成一個群組並允許被裁切，就跟今天一條過長的純文字行一樣。

## 測試

遵循本 repo 邊界優先的測試規則（斷言 pane 與 database，絕不斷言內部）：

- **`furigana` module 單元測試**（純粹、快速）：base-only 渲染去掉讀音與分隔空白；stacked 渲染產生兩條等顯示寬度的行，讀音置中在 base 上方；無標記輸入原樣通過；送假名、相鄰詞、以及讀音比 base 寬各自都正確對齊；畸形的 `[` 留作字面。
- **Host 邊界測試**（透過 `spawn_test_host_with_cards`，重用現在已忠實處理寬字元的 `buffer_text`）：一張 front 為 ` 勉強[べんきょう]` 的卡片，在揭示前顯示 `勉強` 而**不**顯示 `べんきょう`；揭示後 pane 在 `勉強` 正上方那一行包含 `べんきょう`；一張全英文卡片渲染得與今天一模一樣（通過路徑的回歸防護）。
- **折行測試：** 一個長標注句在窄 pane 裡折成單元對齊的讀音／base 對，沒有讀音與它的漢字分離，也沒有任何行超過內寬。

## 要升格為 ADR 的決策

這裡有兩個選擇是持久的，屬於 `docs/adr/`（起草為 ADR-0012；先英文，zh-TW 翻譯隨承接 0001-0011 的同一輪補上）：

1. **Furigana 行內書寫，且純粹是渲染的事。** 卡片模型與 storage 不改；讀音以 Anki 相容標記住在 `front`/`back`，在繪製時解析。被拒絕的替代方案：另設一個 `reading` 欄位，它無法表達一個欄位中多段各自帶讀音的漢字。
2. **讀音只在答案面渲染。** 問題面顯示 base 漢字。這讓一張測驗讀音的卡片保持誠實，與 ADR-0002「表面不得搶先透露複習所要測驗之物」的原則一致。曾考慮並延後一個 config 開關：它會為了一個尚無 dogfooding 要求過的偏好，多加第四個 config key 與一個要驗證的值。

## 範圍之外

- **自動產生讀音**（在 ingest 時用 MeCab／kakasi）。對人名與罕見讀音有損；行內書寫的標記才是誠實的事實來源。之後可以拿它來餵標記。
- **音高重音記號、彩色讀音、每個 deck 的 furigana 預設。** 全都疊在這套標記之上而不與之衝突。
- **直書。** 對橫向的終端機格點來說在範圍之外。
