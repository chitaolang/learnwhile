# Host 是由 producer thread 餵入的單一 event loop；沒有 async runtime

**背景。** Host 有三個獨立的輸入來源，全都會修改同一份 state。Trigger frame 從 unix socket 抵達（ADR-0004、ADR-0007），改變 open-Trigger set。按鍵驅動 Review 狀態機——先 reveal，再評分。而 expiry sweep 必須以自己的週期 timer 執行，這是 ADR-0006 定為硬性要求、而非細節的一點：把 sweep 掛在 frame arrival 上，會讓沒有後續 traffic 的 phantom open 永遠排不掉，而那正是該 ADR 存在要處理的情況。這三者都會碰到 open-Trigger set、in-flight card 或 pane，所以必須有東西把它們序列化。另有兩個限制縮小了選擇：v1 spec 的測試決策要求 socket 與按鍵輸入都能在 host 邊界被觸及，而 ADR-0008 要求 `hook` 路徑保持冷。

**決策。** 每個來源一個 producer thread——socket accept、terminal input、sweep tick——各自把自己的來源翻譯成單一的 `Event` 型別，並送進同一個 `std::sync::mpsc` channel。主執行緒擁有 host 的每一份 state 並串行地消化 event；沒有任何 host state 在執行緒之間共享，也沒有任何東西被鎖保護。Producer thread 不持有 state、不做決策；它們只翻譯與傳送。測試持有 `Sender` 的一份 clone，這就是在沒有接上終端機的情況下注入按鍵事件的方式。已拒絕：**搭配 `select!` 的 tokio**，它是 socket server 的慣用解法，卻為了每個 agent 回合只有寥寥幾個 frame 的工作量帶進一整個 runtime，而且——更關鍵地——把一個 async runtime 放進這個 binary 裡，而 ADR-0008 之所以存在正是要讓它的 hook 路徑保持冷，這會讓那份紀律變成一件要記得的事，而不是結構上就成立的事。也已拒絕：**單一執行緒輪詢** `crossterm::event::poll` 加上 timeout、並搭配一個 non-blocking accept，這不需要任何執行緒，卻把 sweep 時序、輸入延遲與 idle CPU 全部塌縮成一個無法為三者同時調校的 timeout 常數；以及**放在 `Mutex` 後、由每個執行緒觸碰的共享 state**，這會重新引入 channel 正好消除掉的那些交錯。

**後果。** State 的所有權是單執行緒的，所以沒有鎖的紀律會出錯，也沒有 deadlock 需要推敲。Event 排序是全序的，測試可以依賴這點：在某個按鍵之前寫入的 frame，會在它之前被處理。代價是一個近乎閒置的 process 用了三個執行緒，這對本機開發者工具無關緊要。由此衍生兩項義務。第一，producer thread 絕不能把 host 拉垮：依 ADR-0007，一個格式錯誤的 frame 不得殺掉 accept loop，因此失敗邊界是個別連線、而不是執行緒——而真的死掉的 producer thread 必須在 log 檔中可見，而不是無聲地餓死它的輸入。第二，channel 是無界的，所以 back-pressure 不可見；這之所以可接受，只因為依 ADR-0007 自己的推理，frame 量微不足道，而這也是在任何 adapter 發出中途進度 frame 之前該重新檢視的假設。當一個 post-v1 的 Prompt Gate 需要 host 在同一條連線上回覆時（ADR-0004），`Event` 會攜帶已接受的 stream，讓主迴圈可以回覆——這個形狀在不需要第二條 channel 的情況下就容納了它，但 v1 並不實作。
