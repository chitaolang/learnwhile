# Lapse 過的卡片會在同一個 Session 內回來；禁止提前的規則跨 Session 仍然成立

**背景。** ADR-0002 禁止曾經呈現尚未到期的卡片，以維持 FSRS interval 的誠實。那條規則寫在 scheduler 的 API surface 被確認之前，而確認之後改變了它的意涵。`fsrs` crate 只建模長期記憶：`next_states` 在一個由 stability 與 difficulty 組成的 `MemoryState` 之上，回傳以天為粒度的 interval，沒有 learning step，也沒有次日內（sub-day）排程。若照字面解讀 ADR-0002，開發者評為 Again 的卡片會被排到數天之後、在那之前不能顯示——於是失敗一張卡片與通過它，在當天剩下的時間裡會產生相同的體驗。這與 DESIGN_DRAFT §3 的前提格格不入：LearnWhile 的單位不是每日一次的 sitting，而是一個滾動 Session 裡許多次簡短的等待，而失敗回想後的那幾分鐘，正是再次嘗試最有價值的時候。

**決策。** 評為 Again 的卡片會加入一個由當前 Session 擁有的記憶體內 lapse queue。選擇順序變成：lapse queue，其次是真正到期的卡片，再其次是每日上限內的新卡，最後是 idle 狀態。除此之外，re-attempt 在其他每一方面都是一次普通的 Review——它以 `days_elapsed` 為零呼叫 `next_states`、持久化回傳的 state，並附加一列 `review_history`，而這個為零的 elapsed days 正是在 audit trail 中辨識 Session 內重複的依據。卡片一旦被評為 Again 以外的任何評分，就離開 queue。這個 queue 從不持久化：它隨 Session、也隨 host process 一起消滅。已拒絕：**照字面遵守 FSRS interval**，這會讓 ADR-0002 保持完整，代價是上述的複習體驗；**實作 Anki 式的 learning step**，這代表要在 FSRS 旁邊再跑第二個 scheduler、並且要負責兩者之間的互動——正是選擇一個上游 crate 本來要避免的工作；以及**持久化 lapse queue**，這聽起來像是健壯性的提升，卻會把一個 Session 內的便利機制轉成能夠跨天把卡片提前拉出來的持久 state，而那正是 ADR-0002 存在要防止的事。

**後果。** 這是在收窄 ADR-0002，而不是推翻它，而這個收窄正是承載重量的部分：禁止提前複習的規則跨 Session、跨天仍然絕對成立，而這個例外被三重界定——被 Session 界定、被卡片必須是在該 Session 內失敗過界定，以及被 queue 只存在於記憶體中界定。在一個 Session 之內，失敗的卡片可以在其已持久化的到期日之前被呈現；這現在是刻意的行為，不是 bug。FSRS 把 re-attempt 看成一次 elapsed days 為零的複習，crate 接受這一點；至於這對參數擬合是有幫助還是有害，在 Analytics Engine 出現之前無法量測，而 v1 以預設參數執行、沒有任何擬合流程，所以目前沒有任何東西押在它上面。Crash 會失去 queue，受影響的卡片就直接回到各自已持久化的到期日——這是與系統其餘部分一致的 fail-open 結果。`cards.state` 欄位在 v1 維持 `new` 與 `review` 的值域；lapsed 刻意不是它的值之一，因為身在 queue 中是 Session state，不是卡片本身的屬性。
